# 阶段 2：本地规则引擎实施计划

- **版本**：v0.4.1
- **日期**：2026-11-17
- **角色**：ToFu

本文档将阶段 2 拆分为可实施、可测试和可验收的工作项。当前阶段只做本地事件检测与告警，不执行阻断或其他响应动作。

## 1. 阶段目标

实现 agent 对 eBPF 事件进行本地实时判定，并支持规则的增删改查。

### 本阶段交付

- 规则模型、表达式校验与判定引擎。
- PostgreSQL 规则表及规则读写接口。
- agent 启动时加载并编译已启用的规则。
- 命中规则时输出本地告警。
- 告警同时追加到文件，普通事件仍只输出到终端。
- `adr rules` 命令管理规则。
- 单元测试、存储测试、端到端验收说明。

### 暂不包含

- 命中后 kill 进程、封禁网络等响应动作。
- Web 管理界面、gRPC 规则下发、多设备规则同步。
- 规则热更新；规则变更后重启 agent 生效。
- AI 生成规则、自动更新规则或 pgvector 语义匹配。
- 完整的 Sigma/Falco 等外部规则格式兼容。

## 2. 计划编写时的代码基线

- `internal/rule` 目前只有占位文档，尚无规则模型和引擎。
- `cmd/adr` 的 agent 循环目前读取并打印事件，尚未做规则判定。
- `internal/egress/event.go` 定义了 EXEC、PIPE、DNS、SNI 等事件结构。
- `db/schema.sql` 目前只有 events 表；`db/migrations` 尚无实际迁移。
- `go.mod` 已有 pgx 依赖，尚未引入表达式引擎。

当前规则引擎支持已有 Go payload 解析的 `EXEC`、`PIPE`、`DNS`、`SNI` 事件。`EXIT`、`FORK` 尚无 Go payload 解析，因此不允许为它们创建规则。EXEC 规则输入不暴露原始 `Envp`；PIPE 规则可访问截断的 `Data`，启用相关规则前需确认数据敏感性。

## 3. 规则格式与执行模型

### 3.1 规则字段

第一版规则建议包含：

| 字段 | 说明 |
|---|---|
| `id` | 稳定唯一标识 |
| `name` | 人类可读名称 |
| `description` | 规则意图和来源说明 |
| `enabled` | 是否参与判定 |
| `event_type` | 第一版限定为 `EXEC` |
| `severity` | 固定枚举，如 `low`、`medium`、`high` |
| `expression` | 使用受限表达式匹配事件 |
| `source` | 来源标记，如 `local`、`sigma-import` |
| `created_at` / `updated_at` | 创建及更新时间 |

表达式环境使用明确白名单字段，例如 `Comm`、`Argv`、`PID`、`PPID`、`UID`。首批表达式示例：

```text
Argv[0] matches "(^|/)sleep$"
```

这里的示例仅用于验证字段匹配，不代表实际恶意行为规则。生产规则应有明确检测意图，并使用正常与异常样例验证误报。

注意：`EXEC` 事件来自 `sys_enter_execve`，事件中的 `Comm` 是系统调用发生前的当前进程名称，通常不是即将启动的目标程序名。匹配目标命令时应基于 `Argv[0]`，并注意它不是经内核验证的可执行文件路径。

### 3.2 表达式引擎

评估采用 `github.com/expr-lang/expr`（expr），事件字段映射到固定、类型明确的输入对象。新增或更新规则时先编译表达式；编译失败则拒绝写入，并返回规则 ID 与具体错误。agent 启动时编译全部启用规则并缓存编译结果，不得每条事件都重复编译。

首版规则只产生告警，不支持任意脚本、外部函数或副作用。表达式编译时限制可用字段，并为表达式长度、规则数和执行耗时设置合理边界。

### 3.3 判定结果

每次命中产生一条告警，至少包含：

- 事件时间、事件类型、PID/PPID。
- 规则 ID、名称、严重度及来源。
- 最小必要的事件字段。

告警不得包含原始环境变量、凭证或不必要的 argv 内容。具体日志字段应在实现时按数据最小化原则确定。

## 4. 实施工作项

### 工作项 A：规则模型和验证

在 `internal/rule` 中定义规则、事件视图、告警结果和规则校验逻辑。

- 校验必填字段、ID 格式、事件类型、严重度和表达式长度。
- 明确各字段类型，拒绝未知字段及不支持的操作。
- 对 `EXEC` 事件构造精简视图；不将 `Envp` 放入表达式上下文。
- 定义可区分“规则不匹配”和“表达式执行错误”的返回结果。

**完成标准**：规则校验和事件转换有单元测试；非法规则不会进入持久化或运行时规则集。

### 工作项 B：表达式编译与评估

在 `internal/rule` 中实现引擎：

- 启动或规则变更时编译表达式并缓存程序。
- 按事件类型筛选规则，再评估表达式。
- 对一条事件返回全部匹配的告警，不因首条命中而漏掉其他规则。
- 单条规则执行错误应明确记录并处理，不能伪装成“不匹配”。
- 规则集替换应保持一致性，避免事件评估时读到半更新状态。

**完成标准**：合成事件可独立测试，不依赖 root、eBPF 或 PostgreSQL。

### 工作项 C：PostgreSQL 迁移与存储接口

新增 `db/migrations` 迁移，并同步更新 `db/schema.sql`。规则表建议字段：

- `id`（主键）、`name`、`description`
- `enabled`、`event_type`、`severity`、`expression`
- `source`、`created_at`、`updated_at`

为 `enabled`、`event_type` 建立适当索引；不为这些规则字段使用 pgvector。pgvector 用于后续知识库语义检索，不是规则表达式匹配组件。

在 `internal/store` 封装 PostgreSQL 访问，提供创建、读取、更新、删除、列出和加载启用规则的接口。使用参数化 SQL；创建和更新应在事务中完成必要的数据校验与写入。

**完成标准**：迁移可重复执行；存储测试覆盖 CRUD、重复 ID、无效输入及数据库错误。

### 工作项 D：规则管理命令

在 `cmd/adr` 增加 `rules` 子命令，提供 `list`、`add`、`update`、`delete` 等操作。命令通过 `DATABASE_URL` 连接 PostgreSQL，并在写入前验证和编译表达式。

CLI 参数应明确区分规则 ID、事件类型、严重度、启用状态和表达式。失败时输出可操作的错误信息，不静默忽略数据库或校验错误。

**完成标准**：可通过命令新增、列出、修改、删除规则；无效表达式会被拒绝，数据库记录保持原样。

### 工作项 E：接入 agent

agent 启动时连接本机配置的 PostgreSQL，读取启用规则并编译。读取失败或规则无效时明确失败，不以空规则集继续启动。

事件循环中，在完成已有事件解析后将支持的事件转换为规则视图并评估。保留现有事件输出，同时对命中规则打印简洁告警。规则修改后重启 agent 加载新规则；暂不实现热更新。

在部署设计上，阶段 2 以单机本地验证为目标，不应把 PostgreSQL 凭据暴露给不可信设备或公网。多设备部署时应由后续 server 负责规则存储和分发，agent 通过受认证的协议取得规则。

**完成标准**：agent 能加载数据库规则并对实时 EXEC 事件输出告警；数据库不可用时错误明确。

### 工作项 F：文档和配置说明

更新项目 README、规则/存储说明和阶段进度，记录：

- PostgreSQL 初始化、迁移和 `DATABASE_URL` 配置。
- 规则字段、表达式可用字段及命令用法。
- 规则来源、导入审核与更新流程。
- 告警输出范围、已知限制和隐私注意事项。

按仓库规范更新相关 Markdown 元信息版本、日期和角色。

## 5. 测试与验收

### 单元测试

- 命中与未命中的 EXEC 事件。
- 禁用规则、不同事件类型规则不触发。
- 多条规则同时命中。
- 规则新增、更新、删除对后续评估结果的影响。
- 空表达式、语法错误、未知字段、字段类型不匹配被拒绝。
- 事件视图不暴露环境变量。
- 表达式运行错误可见，不被当作普通未命中。

### 集成测试

- 迁移可在空数据库创建规则表。
- 规则 CRUD 与数据库内容一致。
- agent 启动加载规则；修改规则并重启后行为随之改变。
- 数据库断连、迁移缺失或表达式不可编译时产生明确错误。

### 端到端验收步骤

1. 在本机 PostgreSQL 执行迁移并配置 `DATABASE_URL`。
2. 用 `adr rules add` 添加一条无副作用的测试规则。
3. 启动 agent，另一个终端触发对应 EXEC 事件。
4. 确认 agent 输出包含规则 ID、严重度和 PID 的告警。
5. 更新或删除规则并重启 agent，确认告警按新规则变化。
6. 使用普通 Go 单测验证规则引擎，不要求每次测试都加载 eBPF。

最终检查 `gofmt`、`go test ./...`、`go vet ./...` 和 `make build`。

## 6. 公开规则的复用与导入策略

规则不必全部从零编写，可以导入公开规则作为初始检测内容，但不能假设外部规则可直接在本项目运行。

- **SigmaHQ**：通用日志检测规则库，可作为进程命令行检测逻辑的参考；需要将其 log source 和字段映射到本项目的事件字段。
- **Elastic Detection Rules**：适合参考端点和审计场景的检测逻辑；需检查其数据源、字段依赖、版本和许可证。
- **Falco rules**：适合学习容器/运行时行为检测；其事件字段和规则语言与本项目不同，通常需要重写或转换。

建议分三类管理规则：

1. `builtin`：项目维护的默认规则，版本随项目发布。
2. `imported`：从公开规则导入，保留上游来源、规则链接、许可证、上游版本/提交和本地修改记录。
3. `local`：用户自行添加的本地规则。

导入流程应包括：选择候选规则、确认许可证和来源、检查所需遥测字段是否存在、转换表达式、用正常与异常样例测试、审核误报后再启用。不要在 agent 运行时无审核地自动拉取并执行远程规则。

Sigma、Elastic 和 Falco 规则可用于丰富规则来源，但本项目目前只采集有限的 EXEC/PIPE/DNS/SNI 字段；字段缺失时，外部规则无法可靠匹配。阶段 2 可先手工编写少量项目规则并留好 `source` 元数据，随后再实现经过审核的导入/转换工具。

## 7. 阶段完成判定

阶段 2 在以下条件全部满足时完成：

- agent 对实时支持事件进行本地规则判定并输出告警。
- 规则通过 PostgreSQL 持久化，支持增删改查。
- 表达式在保存前验证，启动时编译并缓存。
- 自动化测试覆盖规则判定、持久化和错误路径。
- 文档说明配置、使用、规则来源及已知限制。
- `go test ./...`、`go vet ./...` 和 `make build` 通过。
